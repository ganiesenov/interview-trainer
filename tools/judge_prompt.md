# Судья сопоставления: реальный вопрос → карточка банка

Используется в `tools/import_real.py`: эмбеддинги дают до пяти кандидатов,
решает судья. Вход — JSONL, по строке на вопрос:
`{"rid", "question", "candidates": [{"id", "sim", "q", "points"}]}`.

## Задача

Для каждого реального вопроса с собеседования реши, есть ли в банке карточка,
которая его закрывает. Выбирай только из `candidates` этой строки. Не больше
одной карточки на вопрос.

Представь кандидата, который выучил карточку: её вопрос `q` и пункты `points`.
Сможет ли он ответить на реальный вопрос интервьюера?

- **exact** — да. Сначала разложи вопрос на явно названные части: всё, что
  соединено «и», перечислено через запятую или задано как «какие бывают X»,
  «как выбрать A и B», «как построить таргет и валидацию». exact — только если
  каждая такая часть покрыта `points` (своими словами считается). «Какие бывают X»
  требует, чтобы виды X были названы. Общая формулировка без частей («как
  устроен X», «зачем нужен X») требует только ядра механизма — тогда
  формулировки могут сильно различаться.
  Примеры в скобках — не отдельные части: «чем отличаются оптимизаторы (SGD,
  momentum, Adam)» закрывает карточка, где разобраны SGD с моментом и Adam.
  Части — только то, без чего ответ интервьюера не устроит.
- **partial** — тема та же, но ответа в карточке нет. Интервьюер спрашивает
  явно названный аспект, которого в `points` нет (например, «NDCG против MAP», а
  в карточке MAP не упоминается). Или вопрос — целая задача на проектирование,
  а карточка закрывает только один её кусок. `card_id` — ближайшая из кандидатов.
- **none** — ни один кандидат не про это. Совпадение слов не считается: «инструменты
  для вывода моделей в прод» и «tool calling у LLM» — разные темы. `card_id`: null.

Правила:
- Решай по `q` и `points`, а не по `sim`: косинус часто ставит выше не ту карточку.
- Из нескольких подходящих бери ту, что закрывает вопрос полнее, а не первую.
- HR-вопросы: exact, если карточка отвечает на то же намерение интервьюера, даже
  при другой формулировке («почему подходите на роль у нас» = «почему хотите к
  нам»). Разные предметы — не exact («ожидания от задач» ≠ «зарплатные ожидания»).
- Пустой список `candidates` → none.

## Режим «весь банк»

У bge-m3 на коротких вопросах слабая полнота: «как работает HNSW» и карточка
про Flat/IVF/HNSW дают косинус 0.51. Поэтому неточные совпадения перепроверяются
без эмбеддингов. Вход: `{"rid", "track", "question"}`, без `candidates`.

1. Просмотри оглавление банка `data/real/bank_index.tsv` (id, track, topic, q)
   и выбери до трёх карточек, которые могут закрывать вопрос. Смотри все треки:
   вопрос про A/B может лежать в «Системном дизайне», про attention — в «LLM».
2. Пункты выбранных карточек возьми из `banks/bank_full.json` по id.
3. Реши по тем же правилам exact / partial / none. Кандидаты — только
   выбранные тобой карточки.

## Выход

JSONL, строка на каждый входной вопрос, в том же порядке:

```
{"rid": "r123", "card_id": "dl_init" | null, "match": "exact" | "partial" | "none", "why": "одна короткая фраза"}
```

`why` объясняет решение: что совпало или чего в карточке не хватает.
