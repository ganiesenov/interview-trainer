# Interview Trainer — ТЗ для Claude Code

**Что строим:** локальный тренажёр собеседований на позиции LLM / NLP / DL / AI Engineer. Главная функция — интервьюер, который задаёт вопрос, а потом **не отстаёт**, пока не станет ясно, понимаешь ты решение или пересказываешь туториал.

**Принцип:** v0 должен работать через 2–3 часа. Никакой веб-морды в первой итерации.

---

## Стек

| Слой | Решение | Почему |
|---|---|---|
| Модель | Qwen2.5-32B-Instruct Q4_K_M через Ollama | ~20 ГБ, влезает в 32 ГБ VRAM, ноль стоимости за прогон |
| Альтернатива | Qwen3-32B в режиме thinking | лучше рассуждает при сравнении с эталоном, но медленнее |
| Валидный JSON | `format: "json"` в Ollama, либо GBNF-грамматика в llama.cpp | без этого парсер будет падать на каждом пятом ответе |
| Температура | 0.15 для оценщика, 0.7 для генерации вопросов | оценщик должен быть скучным и повторяемым |
| Генерация банка | опционально: разовый прогон Claude API | разовая стоимость, дальше рантайм полностью локальный |
| Бэкенд v0 | Python CLI (`rich` для вывода) | — |
| Бэкенд v1 | FastAPI + SQLite | стек уже знаком |
| Фронт v1 | один HTML + htmx | без сборки, без роутера |
| Голос (v2) | faster-whisper large-v3 + Silero TTS | локально, GPU всё равно простаивает |

**Главное следствие локального инференса:** модель не должна ничего знать. Всё знание лежит в банке вопросов вместе с эталонами. Модель только сравнивает текст с текстом.

## Режимы

Ключевая идея: **квиз и мок-интервью — это один и тот же движок**. Разница только в `max_followups`.

```
quiz  = вопрос → ответ → оценка                    (max_followups = 0)
mock  = вопрос → ответ → уточняющий ×N → вердикт   (max_followups = 3)
```

Оценщик, формат вопроса и хранилище общие. Сначала строится квиз, мок добавляется параметром и циклом — переписывать ничего не надо.

**Ответ всегда открытый.** Никаких вариантов на выбор: узнавание правильного варианта не равно способности произнести ответ, а валят именно на втором.

1. **`project`** — долбит по твоим проектам из `profile/projects.md`. Главный режим, начинать с него.
2. **`theory`** — attention с выводом, KV-cache, RoPE vs ALiBi, LoRA/QLoRA, квантизация, DPO vs PPO, contrastive learning для эмбеддингов.
3. **`sysdesign`** — «RAG по внутренней документации на 200 rps», «дообучение LLM на домене банка», «оценка качества генерации без разметки».
4. **`coding`** — attention на голом PyTorch, BPE-токенизатор, батчинг с паддингом; плюс лайтовый литкод.
5. **`hr`** — расскажи о себе, почему уходишь, ожидания по деньгам, релокация. Отдельная рубрика: краткость и отсутствие оправданий.
6. **`pitch`** — берёт один проект и заставляет уложиться в 3 минуты. На выходе — расшифровка с пометками, где рассказ провис.

## Промпты (главная часть проекта)

### Интервьюер

```
Ты — senior ML engineer, ведёшь техническое интервью на позицию {role}.
Контекст о кандидате:
{profile}

Правила:
- Один вопрос за раз. Никаких списков и подпунктов.
- После ответа НЕ переходи к новой теме. Задай уточняющий, который вскрывает,
  понимает кандидат решение или повторяет за туториалом.
- Целься в: почему именно такие гиперпараметры, какие альтернативы отбросил и
  по какой причине, как измерял результат, что сломалось и как чинил.
- Если ответ общими словами — скажи об этом прямо и потребуй конкретику:
  цифры, названия, что именно изменилось после правки.
- Не хвали. Не подсказывай. Тон нейтральный.
- Максимум {max_followups} уточняющих, дальше — вердикт.

Выведи только текст вопроса, без преамбулы.
```

### Формат банка вопросов

Знание живёт здесь, а не в модели. `banks/theory.yaml`:

```yaml
- id: kv_cache_01
  topic: inference
  question: "Зачем нужен KV-cache и что он ломает при батчинге?"
  key_points:
    - "на каждом шаге генерации K и V для прошлых токенов не меняются"
    - "без кэша сложность на последовательность O(n^3), с кэшем O(n^2)"
    - "память растёт линейно по длине и по батчу: 2 * n_layers * n_heads * d_head * len"
    - "разная длина в батче даёт фрагментацию — отсюда PagedAttention в vLLM"
  reference: |
    Полный эталонный ответ на 4-6 предложений.
```

Для `project`-режима то же самое, но `key_points` пишешь сам по своим проектам — это и есть основная подготовка.

### Оценщик

Модель ничего не оценивает по своим знаниям. Она сверяет два текста:

```
Вот эталонный ответ и список ключевых пунктов.
Вот ответ кандидата.

Твоя задача — механически сверить. Для каждого пункта из списка определи:
covered — назван явно или своими словами
partial — упомянут, но без сути
missed — отсутствует

Не оценивай по своим знаниям. Не добавляй пунктов, которых нет в списке.
Не хвали. Если пункт назван — просто отметь covered.

Отдельно отметь:
- invented: утверждения кандидата, противоречащие эталону
- hedging: признал ли он, что чего-то не знает, вместо выдумывания

Верни строго JSON, без markdown-обёртки:
{
  "points": [{"point": "...", "status": "covered|partial|missed", "quote": "..."}],
  "invented": ["..."],
  "hedging": true|false,
  "score": <доля covered + 0.5 * partial, округлить до 1-10>
}
```

`score` считается в Python из `points`, а не моделью — локальные модели проставляют баллы наугад.

## Схема БД

```sql
sessions(
  id, mode, role, started_at,
  question, transcript_json,
  score, criteria_json, failed_json
);

weak_spots(
  id, topic, source_session_id,
  hits,              -- сколько раз провалено
  last_seen, next_due
);
```

Очередь повторения: `next_due = last_seen + 2^hits дней`, потолок 14 дней. Без SM-2 и прочей алгоритмики — она тут не окупается.

## Фазы

**v0 — вечер. Квиз.** CLI. Один вопрос из `theory.yaml` или по проекту → печатаешь ответ → оценщик выдаёт JSON с рубрикой и эталонным ответом. `max_followups = 0`. Ничего не сохраняется. Проверка: видно ли из разбора, чего именно не хватило в ответе? Если разбор общий и бесполезный — чинить промпт оценщика, дальше не идти.

**v1 — выходные. Мок-интервью + память.** Тот же движок с `max_followups = 3` и циклом уточняющих. SQLite: сессии, провалы, очередь повторения. Остальные режимы. FastAPI + одна HTML-страница, чтобы гонять квиз с телефона.

**v2 — если реально пользуешься.** Голос: говоришь ответ, Whisper расшифровывает, оценщик дополнительно смотрит на слова-паразиты и время до сути. Экспорт провалов в markdown.

## Чего не делать

- Авторизация, Docker, деплой — приложение на одного человека на одной машине.
- Мобильная версия.
- Генерация вопросов «на все случаи жизни» — банк на 300 вопросов ты не пройдёшь.
- Красивый UI до того, как режим `project` реально работает.

## Первый промпт в Claude Code

> Прочитай `CLAUDE.md` и это ТЗ. Собери **только v0 — режим квиза** на локальной модели через Ollama (`qwen2.5:32b-instruct-q4_K_M`, `format="json"`, temperature 0.15). CLI-скрипт `run.py`: берёт случайный вопрос из `banks/theory.yaml`, показывает его, принимает открытый ответ из stdin, отправляет в оценщик вместе с `key_points` и `reference`, парсит JSON, считает score в Python из статусов пунктов, печатает через `rich` таблицу «covered / partial / missed» и эталон. Заложи `max_followups` в сигнатуру интервьюера, но в v0 он равен 0. Не пиши БД, веб и остальные режимы. Положи в `banks/theory.yaml` 5 вопросов-заглушек в нужном формате для проверки.

## Что положить в `profile/projects.md`

По каждому проекту — одинаковая структура, потому что интервьюер бьёт именно по этим полям:

- **Задача и почему её вообще решали** (бизнес- или научная постановка)
- **Что было до тебя** — baseline и его цифра
- **Решение** — архитектура, ключевые гиперпараметры и обоснование каждого
- **Отброшенные альтернативы** и причина отказа
- **Как мерил** — метрика, выборка, валидация
- **Результат в цифрах**
- **Что сломалось** и как чинил
- **Что сделал бы иначе сейчас**

Последние два пункта — то, на чём разваливается большинство кандидатов. Заполни их честно, иначе тренажёр не сможет по ним бить.
