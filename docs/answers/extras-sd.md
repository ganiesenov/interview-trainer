# Разборы — ML system design: каталог кейсов

Компактный формат: **30 секунд** / **2 минуты** / **ловят на этом**.

---

### `sd_search` — Поиск по каталогу на 10M позиций

**30 секунд.** Двухступенчатая схема: быстрый отбор сотен кандидатов →
дорогое ранжирование. Отбор гибридный: лексический индекс ловит точные
артикулы и редкие слова, векторный — синонимы и описательные запросы.
Ранжирование учитывает не только релевантность: наличие, цена, доставка,
рейтинг продавца, вероятность покупки. Обучение на кликах смещено позицией
показа — нужна поправка на position bias. Отдельные ветки: нулевая выдача,
опечатки, навигационные запросы.

**2 минуты.** Разворачивать по слоям: query understanding
(nl_query_understanding: опечатки, интент, атрибуты в фильтры) → retrieval
(BM25 + ANN, слияние RRF — llm_hybrid) → ranking (LTR на поведенческих и
товарных фичах — ml_l2r; цель ближе к покупке, чем к клику) → бизнес-слой
(буст наличия, дедупликация продавцов). Position bias конкретно: клики
достаются верхним позициям независимо от качества — обучение «в лоб»
закрепляет текущее ранжирование; лечение — модели клика с позицией,
рандомизация пар, инверсии в малой доле трафика (abml-экзплорейшн).
Оценка: офлайн NDCG на размеченных парах + онлайн A/B по конверсии в
покупку с guardrail'ами (latency, нулевые выдачи — st_metricchoice).
Нулевая выдача — отдельный продукт: релаксация фильтров, семантический
fallback, «возможно, вы имели в виду».

**Ловят на этом:**
- *Почему нельзя обучать ранжирование прямо на кликах?* — Position bias +
  петля (показываем → кликают → подтверждаем показ); нужны поправки и
  доля исследования.
- *Запрос «iphone 15 pro 256» не находит товар — где чинить в первую
  очередь?* — Лексическая ветка и парсинг атрибутов: точный артикул должен
  ловиться инвертированным индексом до всякой семантики.

### `sd_reco` — Рекомендации маркетплейса

**30 секунд.** Этапы: отбор кандидатов из миллионов дешёвыми методами
(ANN по эмбеддингам, co-visitation, популярное в сегменте) → ранжирование
сотен тяжёлой моделью → бизнес-правила поверх (доступность, маржинальность,
разнообразие). Холодный старт новых товаров и пользователей — контентные
признаки. Петля обратной связи: показываем то, что модель уже считает
хорошим, — и сами формируем данные.

**2 минуты.** Воронка (recsys_funnel) с числами: 10⁷ товаров → ~500
кандидатов (two-tower эмбеддинги + ANN; несколько источников кандидатов —
персональные, трендовые, категорийные) → ранкер на богатых фичах
(ml_recometrics: цель — вероятность покупки/добавления, не клика) →
переранжирование (разнообразие MMR, бизнес-квоты). Cold start
(ml_coldstart): новый товар — контентные эмбеддинги (текст+фото), новая
сессия — популярное в контексте; exploration-доля для набора статистики.
Петля (op_feedback): непоказанное не получает кликов — счётчики
популярности самоусиливаются; лечение — логировать показы (не только
клики), корректировать на экспозицию, держать случайные слоты. Оценка:
офлайн recall@K по будущим покупкам (с оговоркой смещения), онлайн — GMV/
конверсия с долгосрочным holdout (st_longterm: краткосрочный CTR ≠
LTV).

**Ловят на этом:**
- *Почему две башни, а не кросс-модель на этапе кандидатов?* — Кандидаты
  требуют предвычислимости: эмбеддинги товаров в ANN-индексе, запрос
  пользователя — один прогон; кросс-внимание невозможно на 10⁷
  (llm_lateinteraction — та же экономика).
- *Рекомендации «скатились в бестселлеры» — механизм и лечение?* — Петля
  популярности: показы → клики → буст; экспозиционная коррекция,
  разнообразие в цели, exploration.

### `sd_feed` — Ранжирование ленты

**30 секунд.** Отличия от поиска: запроса нет — намерение восстанавливается
из истории и контекста, а разнообразие — часть целевой функции. Одна
метрика (время просмотра) вырождает ленту — цель многокритериальна. Петля
обратной связи сужает интересы — нужна борьба. Свежесть и холодный старт
контента требуют механизма исследования (иначе новое не наберёт показов).
Задержки жёсткие: кандидаты отбираются заранее, онлайн — лёгкая модель.

**2 минуты.** Многокритериальность конкретно: P(клик), ожидаемое время,
P(лайк/шер/коммент), P(жалоба/скрытие) со знаком минус — взвешенная
комбинация, веса — продуктовая политика (и предмет вечной настройки);
оптимизация чистого watch time даёт кликбейт и думскроллинг — регуляторный
и репутационный риск. Фильтр-пузырь: похожее → клики → ещё похожее;
лечение — разнообразие в переранжировании (MMR, квоты тем), случайные
инъекции, длинные метрики удержания в A/B (краткосрочный CTR может расти
при деградации опыта — st_longterm). Свежий контент: cold-start буст с
быстрым затуханием, exploration-бюджет (доля показов на «недоказанное»),
отдельная модель ранней оценки. Инфраструктура: кандидаты
пересчитываются офлайн/микробатчами (op_serving-гибрид), онлайн-ранкер
лёгкий, фичи из feature store с жёсткой свежестью
(op_featurestore_online).

**Ловят на этом:**
- *Почему у ленты нет «идеальной метрики»?* — Любая одиночная
  оптимизируется в вырождение (время → кликбейт, клики → жёлтые заголовки);
  цель — вектор с политическими весами и guardrail'ами.
- *Как новый автор наберёт аудиторию при ранжировании по engagement?* —
  Никогда без exploration: явный бюджет показов новому + быстрая оценка —
  дизайн-требование, не опция.

### `sd_fraud` — Антифрод реального времени

**30 секунд.** Главные ограничения: решение за десятки миллисекунд;
признаки истории — онлайн по скользящим окнам (velocity); разметка
запаздывает (chargeback) и неполна (не весь фрод выявлен); экстремальный
дисбаланс + адаптивный противник (распределение меняется). Архитектура —
каскад: быстрые правила отсекают очевидное, модель разбирает спорное.

**2 минуты.** Латентный бюджет диктует всё: KV-хранилище онлайн-счётчиков
(op_streaming_infra: event-time окна по карте/девайсу/IP — ml_velocity),
лёгкая модель (бустинг с сотнями фич — не тяжёлые сети), деградация при
недоступности фич (правила — ml_ruleorml как фолбэк). Каскад: белые/чёрные
списки и жёсткие правила (мгновенно, объяснимо) → модель на сером потоке →
очередь аналитиков на пограничном (sd_humanloop). Метки: неполнота
(невыявленный фрод в «чистых») занижает признаки — PU-learning-осторожность;
лаг — обучение со сдвигом, прокси-метки. Противник: дрейф не «естественный»,
а направленный (нащупывают пороги) — быстрый цикл переобучения
(op_retrain: триггеры), правила как быстрый ответ на новую схему (минуты
против дней модели), детекция аномалий для неизвестных схем (ml_anomaly).
Метрика: деньги при ёмкости разбора (ml_costmatrix), FPR на честных
(трение!), и время реакции на новую схему.

**Ловят на этом:**
- *Почему правила не умирают при живой модели?* — Скорость реакции (новая
  схема блокируется правилом за минуты) и объяснимость/аудит; модель ловит
  обобщённые паттерны — роли разные.
- *Как валидировать модель при неполной разметке?* — Отложенная оценка на
  подтверждённых исходах + разбор алертов аналитиками (precision руками) +
  случайные пропуски для честной базы (st_survivor-логика).

### `sd_abuse` — Защита от накрутки

**30 секунд.** Противник адаптивный: статичные правила устаревают, метрики
деградируют незаметно. Ценны сигналы, ДОРОГИЕ для подделки: история
аккаунта, устройство, поведение во времени, связи между аккаунтами.
Графовый анализ выявляет фермы лучше пер-аккаунтных признаков. Реакция
градуированная: ограничение, проверка, задержка — не только блокировка. И
не раскрывать логику детекции в сообщениях пользователю.

**2 минуты.** Экономическая рамка: цель — сделать атаку нерентабельной, не
«поймать всех»; сигналы ранжируются по стоимости подделки (создать 1000
аккаунтов дёшево; 1000 аккаунтов с годовой историей и разными девайсами —
дорого). Граф: общие устройства/IP/платёжные методы/паттерны времени
связывают ферму — кластерные признаки (размер компоненты, плотность) бьют
индивидуальные; графовые эмбеддинги/GNN — следующий этаж (connections-стиль
анализа). Градуированность: мягкие фрикции (капча, задержка, лимит) дешевле
ложного бана и не выдают порог детекции; жёсткое — с ручным подтверждением.
Обратная связь атакующего: сообщение «заблокировано за X» = бесплатный
oracle для перебора обхода — потому generic-ответы (nl_toxicity: та же
гонка). Оценка: канареечные ханипоты, красная команда, доля пойманных
известных схем, и медленные метрики здоровья экосистемы (инфляция лайков).

**Ловят на этом:**
- *Почему точность на исторических атаках переоценивает систему?* —
  Противник уже сменил тактику: оцениваться надо на свежих схемах и
  времени реакции, история — нижняя граница (st_winner для атак).
- *Бан-волна задела честных пользователей — как проектировать реакцию?* —
  Градуировка + обжалование + быстрый откат волны: цена ложного бана
  (отток, суппорт, PR) закладывается в пороги (ml_costmatrix).

### `sd_moderation` — Модерация контента

**30 секунд.** Каскад: дешёвые правила и списки → модель → человек; каждый
уровень отсеивает поток для следующего. Пороги — раздельно по типам
нарушений: цена пропуска угрозы жизни несопоставима со спамом.
Автоудаление — только при очень высокой уверенности; остальное — очередь
модератора с приоритетом. Обратная связь и апелляции: решения модераторов —
обучающие данные и оценка модели. Состязательность: нарушители
подстраиваются — eval-набор обновляется постоянно.

**2 минуты.** Разворачивается как nl_toxicity + операционка: SLA по типам
(угроза — минуты, спам — часы), приоритизация очереди (риск × охват
контента), маршрутизация по языкам и специализации модераторов
(nl_langdetect). Психологическая нагрузка модераторов — реальное
проектное ограничение (ротация, поддержка, автоблюр). Апелляции — двойная
служба: контроль качества (доля отменённых решений по модераторам и
модели — op_labelquality) и источник трудных примеров. Прозрачность
против обхода: публичные правила — да, пороги и фичи — нет (sd_abuse).
Метрики: prevalence вредного контента (случайные аудиты — независимая
оценка), время до удаления по типам, FPR по типам (и по группам —
справедливость, ml_fairness), пропускная способность очереди
(op_capacity).

**Ловят на этом:**
- *Почему один порог на все нарушения — ошибка проектирования?* — Цены
  ошибок различаются на порядки: порог угроз жизни с высоким recall
  (терпим FPR), порог спама — наоборот; ml_thresh по типам.
- *Как мерить то, что НЕ поймали?* — Случайные аудиты потока людьми
  (prevalence), жалобы пользователей с поправкой на смещение, красная
  команда с синтетическими нарушениями.

### `sd_multimodal_prod` — Проверка объявлений фото+текст

**30 секунд.** Модальности проверяются и по отдельности, и СОВМЕСТНО:
несоответствие текста и фото — отдельный тип нарушения (фото айфона, текст
про реплику). Каскад экономит: дешёвые проверки отсеивают очевидное,
тяжёлые модели — на остатке. Быстрая ветка для публикации + медленная
тщательная постфактум. Пороги отдельно по типам нарушений. Контур
обжалования и обучение на решениях модераторов.

**2 минуты.** Слои каскада: хеши известного запрещённого (мгновенно) →
лёгкие пер-модальные модели (текстовый классификатор, image-теггер) →
кросс-модальная сверка (CLIP-подобное соответствие фото↔текст↔категория;
цена/категория/атрибуты — табличные сигналы туда же) → VLM/тяжёлые модели
на спорном → модератор. Two-speed дизайн: публикация не ждёт тяжёлых
проверок (UX!) — мгновенные лёгкие проверки на пути публикации, тяжёлые
асинхронно с депубликацией постфактум (компромисс «время жизни нарушения
против трения продавцов» — явное продуктовое решение). Специфика
маркетплейса: контрафакт (бренд-детекция на фото + прайс-аномалии),
запрещённые категории, дубликаты объявлений (nl_dedup_text +
cv_imgretrieval). Петля: решения модераторов и апелляции → разметка
(op_feedback); прод-метрики: prevalence по типам, время до снятия, доля
ложных депубликаций.

**Ловят на этом:**
- *Зачем кросс-модальная проверка, если каждая модальность чиста?* —
  Нарушение живёт в НЕСООТВЕТСТВИИ (безобидный текст + фото запрещённого
  товара в углу; цена ×10 ниже рынка при люксовом фото) — видно только
  вместе.
- *Публиковать сразу или после проверки?* — Каскадный ответ: мгновенные
  дешёвые проверки блокируют очевидное, остальное публикуется и
  допроверяется; порог этой развилки — бизнес-решение о риске.

### `sd_matching` — Склейка карточек товаров

**30 секунд.** Два этапа: блокирование кандидатов (все пары перебрать
невозможно) и точная попарная классификация. Блокирование — нормализованные
ключи, n-граммы, эмбеддинги названий; здесь важна ПОЛНОТА. Попарная
модель — признаки сходства: названия, атрибуты, цена, изображение,
штрихкоды. Решения сводятся в кластеры транзитивно — одна ошибка склеивает
два больших кластера: пороги + ручная модерация крупных слияний. Метрики
попарно И по кластерам; неверная склейка обычно дороже пропуска.

**2 минуты.** Это entity resolution (nl_normal_entities в квадрате — без
готового справочника, сущности строятся сами). Блокирование: несколько
стратегий параллельно (штрихкод точно; бренд+модель нормализованно;
эмбеддинг-ANN) — union кандидатов, полнота ~99% при тысячах кандидатов на
товар вместо 10¹⁴ пар. Попарная модель: фичи сходства (edit distance
названий, жаккар атрибутов, разница цен в лог-шкале, CLIP-близость фото,
совпадение кодов) → бустинг/кросс-энкодер; калибровка скоров (пороги
дальше — calib). Транзитивная ловушка: A=B, B=C ⇒ A=C — цепочка слабых
решений сливает «iPhone 15» и «iPhone 15 Pro» в мегакластер; лечение —
высокий порог на автослияние, connected components с ограничением
диаметра, крупные слияния — человеку (sd_humanloop), периодическая
переоценка кластеров. Асимметрия цен: неверная склейка показывает
покупателю не тот товар (жалобы, возвраты) — порог смещён к точности;
метрики: pairwise PR + кластерные (B³, доля чистых кластеров).

**Ловят на этом:**
- *Почему полнота важнее точности на блокировании?* — Пропущенная пара
  потеряна навсегда (модель её не увидит); ложный кандидат лишь потратит
  инференс попарной модели.
- *Как одна ошибка портит два кластера и как этого избежать?* —
  Транзитивность: слабое ребро соединяет компоненты — сотни товаров
  перемешаны; порог на слияние КРУПНЫХ компонент выше + ручное
  подтверждение.

### `sd_docai` — Разбор входящих документов

**30 секунд.** Стадийный пайплайн: предобработка изображения → OCR →
определение типа документа → извлечение полей → валидация. Извлечение
опирается не только на текст, но и на КООРДИНАТЫ: таблицы и формы теряют
смысл в плоской строке. Валидация бизнес-правилами (суммы сходятся, ИНН
проходит контрольную сумму, даты в диапазоне) ловит большую часть ошибок
OCR. Ручная проверка при низкой уверенности — порог продуктовый. Метрика
по полям И по документам целиком (документ с одной ошибкой всё равно к
человеку).

**2 минуты.** Разворачивание стадий: предобработка (deskew, contrast,
бинаризация — качество OCR решается здесь), OCR с координатами и
уверенностями (llm_vlmocr: классика против VLM и гибрид), классификация
типа (маршрутизация к своим экстракторам полей), извлечение
(правила/NER по layout-фичам/LayoutLM-класс/VLM — лестница nl_dialogue с
координатным измерением), нормализация (даты, суммы, ИНН — форматы),
валидация (перекрёстные проверки: итог = сумма строк; чексуммы;
справочники контрагентов — nl_normal_entities). STP (straight-through
rate) — главная бизнес-метрика: доля документов без человека; порог
уверенности двигает STP↔ошибки (ml_thresh); поле-уровневые уверенности
(OCR confidence × валидация) маршрутизируют на выборочную проверку ПОЛЕЙ,
не всего документа. Обратная связь: правки операторов — золотая разметка
(op_feedback). Версии шаблонов документов дрейфуют (новые формы) —
мониторинг доли «неизвестный тип» (op_metricstore).

**Ловят на этом:**
- *Почему метрика «95% полей верны» может означать провал?* — При 20 полях
  на документ это ~36% документов без единой ошибки: почти всё идёт к
  человеку; смотреть document-level STP.
- *Что даёт валидация, чего не даст лучшая модель извлечения?* —
  Независимую проверку согласованности: ловит и OCR-ошибку, и галлюцинацию
  VLM, и опечатку в самом документе — дешёвая строка гарантий.

### `sd_kyc` — Проверка клиента при открытии счёта

**30 секунд.** Стадии: распознавание документа → проверка подлинности →
сравнение лица с фото документа → сверка по спискам и справочникам. Цена
ошибок асимметрична: пропуск мошенника — регуляторный риск, отказ
честному — потерянная выручка и репутация. Liveness обязателен: отличить
живого человека от фото/записи/маски. Часть решений — человеку; порог
автоодобрения — продуктово-регуляторный. Полный аудит: что проверялось,
какие модели и версии, кто принял решение.

**2 минуты.** Комбинация разобранных блоков: docai для документа (sd_docai:
поля + подлинность — паттерны защиты, шрифты, MRZ-чексуммы), face
verification 1:1 (cv_metriclearn, cv_faces_privacy: пороги FAR/FRR под
регуляторную рамку, демографический аудит), liveness
(active — моргание/повороты, passive — анализ текстуры/глубины; гонка с
дипфейками — обновляемая), санкционные/PEP-списки (nl_normal_entities:
нечёткое сопоставление имён с транслитерацией — казахстанский контекст с
двумя алфавитами!). Каскадные пороги: авто-одобрение (высокая уверенность
всех стадий) / доппроверка (запрос другого документа, видеозвонок) /
ручной комплаенс / отказ; конверсия онбординга ↔ риск — управляемый
трейдоф (ml_thresh на многомерном скоре). Аудит — регуляторное ядро:
версионирование моделей (op_docs, op_ab_infra), полный лог решения,
воспроизводимость («почему одобрили в марте» — через год). Твой банковский
бэкграунд здесь — прямое преимущество в разговоре.

**Ловят на этом:**
- *Почему liveness — отдельная задача, а не «хорошее сравнение лиц»?* —
  Сравнение отвечает «тот же человек НА ИЗОБРАЖЕНИИ», liveness — «перед
  камерой живой человек»: атака фото/экраном обходит первое при идеальном
  матче.
- *Имя из документа не матчится со списком санкций напрямую — что в
  дизайне?* — Нечёткий и фонетический матчинг с транслитерациями
  (Кирилл/латиница), порог с ручным разбором серой зоны: пропуск listed —
  регуляторная катастрофа.

### `sd_speech` — Голосовой ассистент

**30 секунд.** Цепочка ASR → LLM → TTS: задержки складываются —
воспринимаемое время снижается ПОТОКОВОЙ обработкой на каждом этапе. Ошибки
ASR каскадно портят понимание — модель должна быть устойчива к «опечаткам»
распознавания и омофонам. Детекция конца реплики критична: агрессивная
перебивает, мягкая создаёт паузы. Доменная лексика (имена, названия,
номера) — подсказки и словари в ASR. Метрики по всей цепочке: WER на
входе, успешность задачи на выходе, задержка до первого звука.

**2 минуты.** Латентный бюджет (latency_budget): стриминговый ASR
(частичные гипотезы) → LLM начинает на незавершённой реплике (или
мгновенно после endpoint) → стриминговый TTS с первого предложения
(llm_streaming: TTFT-логика на голосе — время до первого ЗВУКА); целевой
E2E — сотни миллисекунд, иначе диалог «неживой». Endpoint detection:
пауза ≠ конец мысли (числа диктуют с паузами!) — семантический endpointing
(модель решает, закончена ли мысль) поверх акустического. Каскад ошибок:
WER 10% → критичные сущности (суммы, номера) искажаются — подтверждение
критичного переспросом (sd_docai-валидация голосом), biasing-словари
(контакты, продукты — nl_glossary в ASR), N-best гипотезы в LLM.
Barge-in (перебивание ассистента) — обязателен UX-ом. Метрики: WER
(по-доменно!), task success rate, латентности по стадиям, доля
переспросов; твой казахский контекст — code-switching и локальные имена
(nl_langdetect) как главная сложность ASR.

**Ловят на этом:**
- *Почему полный WER — слабая метрика для ассистента?* — Ошибка в
  предлоге безвредна, в сумме платежа — фатальна: нужны entity-WER и
  task success (nl_ner_eval-логика на голосе).
- *Где в цепочке прячется главная задержка и как её едят?* — Ожидание
  конца реплики + первый токен LLM: семантический endpointing,
  спекулятивный старт на частичной гипотезе, стриминг всего.

### `sd_forecast` — Прогноз спроса на десятки тысяч SKU

**30 секунд.** Глобальная модель на всех рядах: переносит паттерны между
товарами, спасает короткие ряды и новинки (ml_arimaml: победа
LightGBM-подхода в M5). Валидация — только по времени, несколько срезов,
горизонт = реальному горизонту планирования. Бизнесу нужен КВАНТИЛЬ:
уровень запаса определяется допустимой вероятностью дефицита. Праздники,
промо, дефициты — признаками. Продажи ≠ спрос: в out-of-stock дни спрос
был, а продажи ноль — коррекция обязательна.

**2 минуты.** Квантильная постановка (ml_quantile): сервис-левел 95% =
прогноз 95-го квантиля спроса (pinball loss); недопрогноз = дефицит и
потерянные продажи, перепрогноз = замороженный капитал и списания —
асимметрия задаётся квантилем по категории (молоко ≠ электроника).
Цензура спроса: OOS-дни занижают историю → модель учит заниженный спрос →
снова дефицит (самоусиление); коррекция — восстановление спроса по
аналогам/доле дней в наличии, флаг OOS в признаки (ml_tsfeat: признаки
событий). Иерархия: SKU × магазин × регион — согласование прогнозов
(reconciliation), новинки — по аналогам (атрибутные эмбеддинги,
ml_coldstart). Оценка: wMAPE/квантильные лоссы по срезам времени И по
сегментам (ABC-классы), плюс бизнес-метрики симуляцией запасов (сервис-левел,
списания). Пайплайн: ежедневный батч (op_batch_pipeline), мониторинг
деградации по горизонтам.

**Ловят на этом:**
- *Почему средний прогноз бесполезен для запасов?* — Решение о запасе —
  квантильное по построению (вероятность дефицита); среднее не говорит,
  сколько держать (st_cipi: предсказательный интервал, не точка).
- *Как учесть промо, если их календарь неполон?* — Промо-признаки из
  систем планирования (будущее известно — законный признак будущего,
  ml_tsfeat); неполнота календаря = главный источник ошибок — процессная
  проблема, не модельная.

### `sd_pricing` — Динамическое ценообразование

**30 секунд.** Ядро — модель спроса: как вероятность покупки зависит от
цены при прочих равных. Исторические данные почти всегда недостаточны:
цены менялись НЕ случайно (эндогенность — st_endog). Нужен механизм
исследования: контролируемые ценовые эксперименты на части трафика.
Обязательны ограничения: минимальная маржа, ценовая политика,
справедливость, репутационные риски. Метрика — долгосрочная ценность, не
выручка за сессию: агрессивные цены разрушают доверие.

**2 минуты.** Эндогенность конкретно: цены поднимали при высоком спросе
(сезон) → в данных корреляция «выше цена — выше продажи» → наивная модель
рекомендует поднимать всегда; причинная эластичность требует ЭКЗОГЕННОЙ
вариации — эксперименты (рандомизация цен в коридоре по
товарам/регионам/времени — st_interference: осторожно с перетоками),
инструменты (косты поставщика — st_endog), природные эксперименты.
Оптимизация: эластичность по сегментам × ограничения (маржа, MAP-политики,
психологические пороги 990/1000) → цена; explore-exploit постоянен (рынок
дрейфует — st_bandit с оговорками об отложенных эффектах). Справедливость и
репутация: персональные цены — регуляторно-репутационное минное поле
(дискриминация! — ml_fairness), прозрачность динамики (сурджи такси
объясняются); метрика — LTV и доверие (повторные покупки), краткосрочная
выручка как единственная цель — самоубийство бренда (sd_feed-урок про
вырождение одной метрики).

**Ловят на этом:**
- *Почему модель на истории цен даёт абсурдную эластичность?* —
  Эндогенность: цены следовали за спросом; лечится только экзогенной
  вариацией (эксперимент/инструмент), не бо́льшими данными.
- *Какие ограничения зашиваются ЖЁСТКО, вне оптимизатора?* — Минимальная
  маржа, юридические политики, запрет дискриминационной персонализации —
  guardrails кодом (sd_agent_prod-принцип: критичное не делегируют
  модели).

### `sd_routing` — Прогноз времени доставки

**30 секунд.** Декомпозиция: сборка + ожидание курьера + дорога +
передача — каждая составляющая моделируется отдельно. Нужен КВАНТИЛЬ, не
среднее: обещание должно выполняться в заданной доле случаев. Прогноз
влияет на систему и пользователей — обратная связь (обещали дольше —
заказали меньше). Данные цензурированы и смещены: отменённые и
неназначенные заказы известны неполно. Оценивать: точность + долю
выполненных обещаний + последствия опоздания.

**2 минуты.** Декомпозиция работает как sd_forecast+ml_ltv: у стадий разные
источники (сборка — от ресторана/магазина и корзины; дорога — от карт и
трафика; ожидание — от баланса спрос/предложение курьеров) и разные модели;
сумма квантилей ≠ квантиль суммы — финальное обещание собирается
симуляцией/квантильной моделью поверх. Обратная связь двойная: обещание
меняет конверсию (длинное — отток заказа) и поведение системы
(диспетчеризация подстраивается) — abml-мир; оценка новой модели прогноза —
только A/B (офлайн-точность не видит поведенческих эффектов). Цензура:
отменённые до назначения заказы — нет полного времени (st_survivor);
обучение на завершённых смещено к удачным. Продуктовые метрики: on-time
rate (доля в обещание), lateness cost (компенсации, отток —
асимметрия! ml_regmetric: MAPE наказывает не то), и конверсия от
показанного обещания — прогноз здесь продукт, не отчёт.

**Ловят на этом:**
- *Показывать честный p50 или консервативный p90?* — Трейдоф конверсии и
  on-time: длинное обещание теряет заказы, короткое — доверие; квантиль —
  продуктовый параметр, возможно сегментный.
- *Почему офлайн-MAE не предскажет успех новой модели?* — Прогноз меняет
  поведение (конверсию, диспетчеризацию): эффект виден только в
  эксперименте с поведенческими метриками.

### `sd_queue` — Приоритизация обращений в поддержке

**30 секунд.** Приоритет = срочность × влияние на клиента × вероятность
эскалации; модель предсказывает составляющие, ПРАВИЛО превращает их в
очередь. Гарантии низкоприоритетным обязательны — иначе они не будут
обработаны никогда (starvation). Петля: приоритет влияет на время ответа,
время — на исход: обучение на истории смещено. Метрика — не точность
модели, а суммарное время ожидания и доля нарушенных обязательств.

**2 минуты.** Разделение «модель предсказывает — правило решает»
(ml_costmatrix-принцип): предсказания (тема — nl_stopcriteria, тональность/
эскалация, SLA-класс клиента) собираются в скор интерпретируемой формулой —
изменение политики (поднять вес VIP) не требует переобучения. Анти-старвация:
aging (приоритет растёт со временем ожидания), квоты на классы, жёсткие
SLA-дедлайны поверх скора (llm_queue: те же механизмы). Петля смещения:
«низкий приоритет → долгий ответ → отток» учит модель, что такие тикеты
«неважны» (op_feedback: обучение на своих решениях) — лечится случайной
долей и каузальной осторожностью. Операционные метрики: взвешенное время
ожидания, доля нарушенных SLA, точность маршрутизации (не classification
accuracy — она прокси); и мониторинг сдвига потока (новый продукт — новые
темы — nl_intentood: unknown-тикеты).

**Ловят на этом:**
- *Почему «точность классификации приоритета» — не метрика системы?* —
  Система оптимизирует ОЧЕРЕДЬ: ошибка на границе классов с равным
  временем безвредна, редкая ошибка на критичном — катастрофа; мерить
  исходы очереди.
- *Как не дать модели «похоронить» тихих клиентов?* — Aging + квоты +
  случайная выборка на разбор: структурные гарантии вместо надежды на
  модель.

### `sd_alerts_ops` — Предиктивное обслуживание

**30 секунд.** Целевое событие редкое, телеметрия огромна — узкое место не
объём сигналов, а РАЗМЕТКА ОТКАЗОВ (журналы ремонтов, их качество).
Постановка — «отказ в горизонте H» с явным окном признаков и отступом
(успеть среагировать). Признаки — динамика: тренды, отклонения от нормы
КОНКРЕТНОГО агрегата, не абсолютные значения. Асимметрия: ложная тревога —
осмотр, пропуск — простой или авария. Оценка — и качество, и полезность:
успел ли персонал среагировать.

**2 минуты.** Конструкция таргета (ml_churndef-скелет): окно признаков →
gap (время на реакцию: предсказание за час до отказа бесполезно, если
ремонт занимает день) → окно события; разметка из ремонтных журналов
шумная (ремонт ≠ отказ, даты приблизительны — nl_annotate-проблемы в
железе). Нормализация на агрегат: «вибрация 5мм/с» — норма одному станку,
тревога другому — отклонения от собственного бейзлайна (ml_velocity:
отклонение от своей нормы), возраст/режим эксплуатации в признаки.
Холодный старт постановки: пока отказов мало — anomaly detection
(ml_anomaly) как первая ступень, сбор разметки, переход к supervised.
Survival-взгляд: время до отказа с цензурой (ml_survival) — богаче
бинарной постановки. Метрика полезности: PR при ёмкости осмотров
(ml_thresh: топ-K по бюджету бригад), lead time распределение
(предупредили ли ВОВРЕМЯ), предотвращённые простои в деньгах — продать
систему можно только этим числом.

**Ловят на этом:**
- *Данных — терабайты телеметрии, а модель не учится. Что не так?* —
  Отказов десятки, и их разметка кривая: узкое место — таргет; чинить
  журналы ремонтов и постановку, не добавлять сенсоры.
- *Зачем gap между признаками и событием?* — Без него модель «предсказывает»
  по предвестникам, при которых реагировать уже поздно; и утечка
  пост-фактумных сигналов (leak).

### `sd_migrate` — Замена эвристики моделью

**30 секунд.** Сначала ИЗМЕРИТЬ текущую эвристику: без честной оценки
нельзя доказать улучшение. Модель — в теневой режим: сравнение решений с
эвристикой на реальном потоке. Расхождения разбираются ВРУЧНУЮ: показывают
и слабости модели, и неожиданные достоинства правил. Выкатка постепенная —
с сегмента максимального выигрыша при минимальном риске. Эвристику
сохранить: резервный вариант и ограничитель для очевидно неверных
предсказаний.

**2 минуты.** Политика измерения: эвристика годами не оценивалась —
базовые метрики на текущем потоке (иногда выясняется, что она лучше, чем
думали, или что «проблема» — в данных). Shadow (op_cicd_ml): матрица
согласия модель×эвристика; ячейки расхождения — золото анализа
(модель лучше / правило лучше / оба врут — по выборке вручную,
ml_erroranalysis); заодно распределения, латентность, доля отказов
модели. Сегментная выкатка: где расхождения в пользу модели
максимальны и цена ошибки умеренна — там канарейка (canary_ladder);
guardrails из эвристики остаются (санитарные границы: «скор > X при
правиле-запрете — блок», ml_ruleorml: правила как ограничители). Откат —
одним переключателем (op_ab_infra). Политически: эвристика — чьё-то
детище; разбор «где правила умнее модели» делает автора союзником, а
находки — фичами модели.

**Ловят на этом:**
- *Shadow показал согласие 92% — что дальше?* — Разбирать 8%: если модель
  права в большинстве расхождений — выигрыш втрое больше видимого; если
  поровну — выигрыша может не быть вовсе.
- *Когда эвристику можно наконец удалить?* — Практически никогда целиком:
  фолбэк при деградации модели и жёсткие ограничители остаются
  (op_serving: деградация проектируется).

### `sd_humanloop` — Человек в контуре

**30 секунд.** Человеку — то, где модель неуверенна или цена ошибки высока,
а не случайная доля. Интерфейс показывает ПРИЧИНУ сомнения и контекст —
иначе проверка медленная и формальная. Решения человека возвращаются в
обучение — иначе система не улучшается. Автоматизационное смещение: люди
склонны соглашаться с предложением машины — контролировать. Доля ручной
проверки — управляемый параметр, связывающий качество и стоимость.

**2 минуты.** Маршрутизация: скор неуверенности (калиброванный — calib,
llm_uncertainty) + бизнес-цена кейса (крупная сумма — человеку независимо
от уверенности) → очередь с приоритетами (sd_queue); кривая
«качество↔доля ручного» строится по порогу и отдаётся бизнесу как ручка
(selective prediction — риск-каверидж). Интерфейс — половина системы:
подсветка причины (какие поля сомнительны — sd_docai; какой фрагмент
текста — подсветка), контекст рядом (не «открой три системы»), решение в
один клик; скорость ревью = стоимость системы. Automation bias
(cv_annotation_tools: якорение): доля слепых проверок (без показа
предсказания) меряет сдвиг; UI без «предвыбранного» ответа на критичных.
Петля: решения → разметка (op_feedback) с контролем качества самих
ревьюеров (op_labelquality); и мониторинг доли ручного как метрика дрейфа
(растёт — модель деградирует или поток изменился — op_metricstore).

**Ловят на этом:**
- *Почему «случайные 5% на проверку» — плохой дизайн?* — Ревью тратится на
  лёгкие кейсы: неуверенные и дорогие идут в прод без глаз; маршрутизация
  по неуверенности×цене на порядок эффективнее.
- *Как заметить, что ревьюеры «штампуют» согласие?* — Слепые вставки (без
  предсказания) и контрольки с известным ответом: расхождение доли
  исправлений — величина automation bias.

### `sd_multitenant` — ML-сервис для многих клиентов

**30 секунд.** Изоляция данных — базовое требование: ни один клиент не
влияет на результаты другого. Общая модель дешевле и лучше для МАЛЫХ
клиентов (перенос), персональная точнее для КРУПНЫХ. Гибрид: общая база +
лёгкая адаптация (отдельные веса, пороги, фичи клиента). Метрики и
мониторинг — в разрезе клиентов: провал одного тонет в среднем. Обновления
управляемые: крупным нужна предсказуемость, а не свежесть.

**2 минуты.** Изоляция по слоям: данные (физическая/логическая сепарация,
доступы — op_secrets), признаки (фичестор с tenant-ключом), обучение
(данные клиента А не в модели клиента Б — договорное требование;
федеративный компромисс: общая модель на агрегатах с явного согласия).
Кривая персонализации: малый клиент выигрывает от общей модели (его данных
мало — перенос, ml_datasize), крупный — от своей (домен-специфика);
гибрид — общий энкодер + клиентские головы/пороги/калибровка (llm_lorarank:
адаптеры per-tenant — дешёвая персонализация LLM-мира). Пер-тенантные
метрики (op_metricstore разрезом): SLA по клиентам, алерты на клиентские
деградации (дрейф у одного — его специфика или предвестник общего).
Version pinning: releases клиентам по расписанию с release notes
(llm_provider_upgrade: мы — провайдер), canary на добровольцах, право
клиента остаться на версии (op_multimodel умножается на тенантов —
стандартизация критична).

**Ловят на этом:**
- *Клиент требует «наши данные не должны улучшать конкурентов» — что это
  меняет?* — Запрет кросс-тенантного обучения: общая модель только на
  собственных/согласованных данных, персональная адаптация в изоляции —
  архитектура и договоры.
- *Средние метрики отличные, один клиент грозит уходом — как не
  доводить?* — Пер-тенантный мониторинг с алертами и внутренними SLA:
  «среднее по больнице» скрывает клиентские провалы by design.

### `sd_offline_first` — ML без сети

**30 секунд.** Модель — на устройстве, в его ресурсах (cv_quant:
квантизация, мобильные архитектуры). Обновления отложенные: в парке
одновременно живут разные версии. Данные для обучения собираются с
задержкой и неполно — картина использования искажена. Конфликты локальных
решений при синхронизации — нужна стратегия разрешения. Приватность
улучшается (данные не покидают устройство) — может быть главным
аргументом.

**2 минуты.** Дизайн под парк версий: сервер обязан принимать телеметрию
и данные от ЛЮБОЙ живой версии (совместимость схем — op_datacontract во
времени), фичи и пороги — с моделью в бандле (рассинхрон фич/модели —
классическая поломка, op_ab_infra: версия пары). Смещение телеметрии:
синхронизируются активные онлайн-пользователи — офлайн-ядро (ради которого
всё) недопредставлено (st_selection); выводы о использовании — с
поправкой. Конфликты: локальная классификация/решение против серверной
переоценки после синка — политика «кто прав» (обычно сервер, с
уведомлением), идемпотентность применения (op_pipeline). OTA-обновления
моделей: staged rollout, откат, подпись артефактов (cv_edge: парк-
менеджмент); федеративное обучение — опция для приватного улучшения
(агрегация градиентов без сырых данных) — упомянуть с оговорками о
сложности. Твой контекст: телефонная работа приложения в казахстанских
реалиях связи — живой пример аргументации.

**Ловят на этом:**
- *Чем офлайн-режим ломает A/B-эксперименты?* — Назначение и метрики
  доезжают с задержкой и неполно (смещение к онлайн-юзерам); анализ с
  поправками, длинные окна, иногда — только когортные сравнения.
- *Что кладётся в бандл обновления кроме весов?* — Версия препроцессинга/
  фич, пороги, калибровка, словари — модель без своего окружения
  бессмысленна (согласованность train/serve на устройстве).

### `sd_realtime_ml` — Настоящий real-time или почти

**30 секунд.** Критерий: изменится ли РЕШЕНИЕ от свежести данных на
минуты? Настоящий real-time дорог: потоковая обработка, состояние,
гарантии доставки, дежурства (op_streaming_infra). Микробатчи с задержкой
в минуты покрывают большинство аналитических и рекомендательных сценариев.
Миллисекунды честно нужны: антифрод, торги, безопасность — решение в
момент события. Гибрид оптимален: критичные признаки на потоке, остальные
периодически.

**2 минуты.** Вопрос-фильтр к каждому «нам нужен реалтайм»: покажите
решение, которое изменится от свежести в минуту — рекомендация «товар из
корзины» переживёт 5 минут задержки (микробатч в 100 раз дешевле), блок
транзакции — нет (sd_fraud). Ценник настоящего потока: exactly-once,
состояние окон, восстановление, дежурства (op_oncall), сложность отладки —
инженерная команда, не библиотека. Гибридная архитектура (норма):
медленные фичи (профили, агрегаты за месяц) — батч в фичестор
(op_featurestore_online), быстрые (счётчики минут) — поток; модель
получает смесь с явными SLA свежести по каждой фиче (мониторинг свежести —
op_batch_pipeline). Lambda/Kappa-религии упоминать не обязательно —
важнее умение посчитать цену задержки в деньгах решения (op_serving:
батч против онлайна — тот же выбор уровнем ниже).

**Ловят на этом:**
- *Продакт говорит «хотим реалтайм-дашборд» — что уточнить?* — Какое
  решение принимается по нему и его цена задержки: смотреть раз в час на
  «реалтайм»-цифры — микробатч без дежурств.
- *Какая фича реально требует потока в рекомендациях?* — Сессионный
  контекст (только что смотрел) — минуты решают; профильные вкусы — нет;
  разделение фич по свежести и есть дизайн.

### `sd_lakehouse` — Хранение данных для ML

**30 секунд.** Слои: сырое (immutable — ошибку обработки чинит только
повторный проход по сырому), очищенное, витрины признаков — у каждого слоя
понятная ответственность. Витрины описываются контрактами и версионируются
(op_datacontract, op_datavers) — иначе модели ломаются при изменениях.
Единые определения признаков в обучении и проде
(op_featurestore_online — train/serve consistency). Права доступа и
каталог — с самого начала, не после первой утечки.

**2 минуты.** Bronze/silver/gold-логика с ML-акцентом: сырой слой —
страховка (переигрывание истории при любой ошибке пайплайна —
op_backfill: point-in-time), очищенный — типизация/дедуп/качество
(op_dataquality_metrics на швах), витрины — фичи с владельцами,
lineage и SLA свежести. Версии витрин: смена определения фичи = новая
версия, старая живёт до миграции потребителей (nl_versioning_text-дисциплина
для данных); эксперименты ссылаются на снимки (op_experiment_track).
Каталог/lineage: «кто потребляет фичу X» — ответ до её изменения
(op_deprecate фич), поиск существующих фич против дублей. Доступы:
PII-зоны, row/column-level права, аудит (op_secrets, op_privacy_ops:
right-to-erasure требует знать, ГДЕ данные). Аргумент «с начала»:
ретрофит каталога и прав на живом болоте — кратно дороже; это
op_smallteam-баланс — слоёв минимум, но сырое+версии+доступы
закладываются сразу.

**Ловят на этом:**
- *Почему сырой слой «неприкосновенен»?* — Любая обработка содержит
  ошибки; сырое — единственный источник, из которого можно пересчитать
  правильно; потерял сырое — потерял правду.
- *Фичестор или витрины на parquet — как решить?* — По числу
  онлайн-моделей и общих фич (op_featurestore_online): одна батч-модель —
  parquet и дисциплина; несколько онлайн — фичестор окупается.

### `sd_experiment_platform` — Платформа A/B-экспериментов

**30 секунд.** Состав: единая рандомизация (детерминированная, с проверкой
перекосов — SRM); каталог метрик с однозначными определениями
(сопоставимость между командами); автоматический расчёт значимости с
правильной обработкой ratio-метрик и множественности; guardrail-метрики в
каждом эксперименте независимо от его цели; регулярные A/A-прогоны и
мониторинг здоровья самой платформы.

**2 минуты.** Это продуктовизация всей статистической дисциплины
(l_ab_advanced): рандомизация — hash(unit, salt) со слоями для
параллельных экспериментов (op_ab_infra), SRM-алерт на каждый эксперимент
автоматически (st_aa: перекос сплита = мусорные результаты); каталог
метрик — единые определения и юниты анализа (st_guardrail_ratio: сессии
против пользователей — зафиксировано в метрике, не в голове аналитика);
движок — дельта-метод/бутстрап для ratio, CUPED из коробки (st_varred),
поправки множественности (st_multiarm), sequential-опции (st_seq);
guardrail'ы (latency, ошибки, отписки) считаются всем без запроса
(st_metricchoice). Здоровье платформы: A/A-прогоны пачками
(равномерность p-value), мониторинг логирования. Культурный слой,
который отличает зрелый ответ: платформа демократизирует эксперименты —
и стандартизует честность (без неё каждая команда изобретает свои
ошибки); шаблоны дизайна, обязательная длительность, ревью для
high-stakes.

**Ловят на этом:**
- *С чего начинать платформу в компании без неё?* — Рандомизация + SRM +
  каталог из 5 ключевых метрик + автоотчёт: ядро честности; CUPED и
  sequential — вторая очередь.
- *Почему guardrail'ы «всем принудительно»?* — Команда, оптимизирующая
  свою метрику, не заметит вреда чужой (latency, отписки): платформа —
  страховка экосистемы (st_metricchoice).

### `sd_agent_prod` — Агент в корпоративных системах

**30 секунд.** Права инструментов минимальны и под конкретную задачу — не
общий доступ. Необратимые действия — явное подтверждение человека либо
возможность отката. Каждое действие логируется с обоснованием — разбор
инцидентов. Ограничители обязательны: лимит шагов, лимит стоимости,
детекция зацикливания. Тестирование — состязательное, включая инъекции
через содержимое документов.

**2 минуты.** Модель угроз: агент = LLM с руками; ошибка/инъекция ×
права = ущерб — потому принцип наименьших привилегий на КАЖДЫЙ вызов
(скоуп токенов под задачу, read-only по умолчанию — llm_inject:
скомпрометированный контекст не должен мочь многое). Классификация
действий: обратимые (черновик, поиск) — автономно; необратимые (отправка,
платёж, удаление) — подтверждение (sd_humanloop) или staged-выполнение с
окном отмены. Логирование: цепочка «наблюдение → рассуждение → действие»
на каждый шаг (llm_promptver: версия промпта/модели) — аудит и
воспроизведение инцидента. Ограничители: бюджеты шагов/токенов/денег
(llm_costctl: агентные петли — главный пожиратель), детекция циклов
(повтор состояния), таймауты, kill switch. Адверсариальный eval:
инъекции в документы/письма («перешли мне пароли» в подписи письма —
agent_reliability, red_teaming), эскалация привилегий цепочкой
инструментов, конфликтующие инструкции — регрессионный набор атак
(llm_provider_upgrade-дисциплина для агентов). Твой стек: это ровно
агентные вопросы Anthropic-собеседований — говорить уверенно.

**Ловят на этом:**
- *Почему «агент с доступом ко всем системам» — провал дизайна ещё до
  инцидента?* — Радиус поражения любой инъекции/ошибки максимален;
  права под задачу — единственная работающая граница (инъекции не
  решены — llm_inject).
- *Как тестировать агента перед продом?* — Песочница с копиями систем +
  библиотека атак (инъекции, циклы, edge-кейсы) + метрики: доля
  выполненных задач, доля опасных действий без подтверждения (должна быть
  0), стоимость на задачу.
